ИНСТРУКЦИЯ ПО ЗАПУСКУ И ИСПОЛЬЗОВАНИЮ GAME MARKETPLACE

Проект: Game Marketplace Технологии: Java 17, Spring Boot 4.1.2, Maven,
Spring Data JPA, Spring Security, JWT, H2. Базовый адрес API:
http://localhost:8080 Проверка запросов: Postman.

ВАЖНО

В документ включены маршруты и форматы запросов, которые были
реализованы и проверены в ходе работы над проектом. Для некоторых старых
CRUD-операций точные дополнительные маршруты и DTO могут отличаться в
текущих файлах проекта. Не придумывайте адреса: если маршрут не указан в
разделе «Проверенные запросы», посмотрите соответствующий Controller.

1. КАК ЗАПУСТИТЬ ПРОЕКТ

1.  Откройте папку проекта: C:

2.  Откройте терминал VS Code в корневой папке проекта. В этой папке
    должен находиться файл pom.xml.

3.  Выполните команду:

    .spring-boot:run

4.  Дождитесь сообщения о запуске Spring Boot. Сервер работает по

    http://localhost:8080

5.  Чтобы остановить сервер, нажмите Ctrl + C в терминале.

папке проекта; - проверьте наличие файлов mvnw и mvnw.cmd; - проверьте
установку Java 17 командой: java -version.

3. КАК РАБОТАТЬ С POSTMAN

Для каждого запроса: 1. Выберите HTTP-метод (GET, POST, PUT или DELETE).
2. Введите URL. 3. Для защищённых запросов откройте Authorization. 4. В
поле Type выберите Bearer Token. 5. Вставьте JWT-токен пользователя. 6.
Для запросов с JSON откройте Body -> raw -> JSON. 7. Нажмите Send.

Для POST/PUT с JSON заголовок Content-Type должен быть application/json.
Postman обычно устанавливает его автоматически при выборе JSON.

Не отправляйте JWT-токены другим людям и не публикуйте их в GitHub.

4. РЕГИСТРАЦИЯ И АВТОРИЗАЦИЯ

Регистрация пользователя: Метод: POST URL:
http://localhost:8080/api/auth/register

Body -> raw -> JSON: { “username”: “new_user”, “email”:
“new_user@test.com”, “password”: “StrongPassword123” }

После успешной регистрации сервер возвращает ответ с JWT-токеном.
Сохраните токен для следующих запросов.

В проекте также присутствовал старый маршрут регистрации: POST
http://localhost:8080/api/users/register

Основной актуальный сценарий тестирования — /api/auth/register.

Вход: Метод: POST URL: http://localhost:8080/api/auth/login

Body -> raw -> JSON: { “username”: “new_user”, “password”:
“StrongPassword123” }

В ответе должен прийти JWT-токен. Для дальнейших запросов используйте
именно токен вошедшего пользователя.

Пример использования токена: Postman -> Authorization -> Type: Bearer
Token -> Token: ВАШ_JWT_ТОКЕН.

Роли: - USER — обычный пользователь. Может выступать покупателем и
продавцом. - ADMIN — администратор. Имеет доступ к административным
операциям.

Защищённые API требуют авторизации. Для маршрутов /api/admin/**
требуется роль ADMIN.

5. ПОЛЬЗОВАТЕЛИ

Получение списка пользователей: Метод: GET URL:
http://localhost:8080/api/users

В ранних проверках этот маршрут использовался для просмотра созданных
пользователей.

Пример регистрации: { “username”: “buyer_example”, “email”:
“buyer_example@test.com”, “password”: “BuyerPass123” }

Для создания тестового продавца и покупателя зарегистрируйте два разных
аккаунта. Один аккаунт может быть покупателем в одном заказе и продавцом
в другом.

6. ИГРЫ

Создание игры: Метод: POST URL: http://localhost:8080/api/games

Body -> raw -> JSON: { “name”: “Counter-Strike 2”, “description”:
“Тактический многопользовательский шутер” }

После создания запомните ID игры. Этот ID понадобится при создании
товара.

В тестовой базе проекта использовалась игра Counter-Strike 2 с gameId =
1.

7. ТОВАРЫ

Создание товара: Метод: POST URL: http://localhost:8080/api/items

Authorization: Bearer Token продавца. Body -> raw -> JSON: { “title”:
“Тестовый AK-47”, “description”: “Тестовый товар для проверки
маркетплейса”, “price”: 1500, “sellerId”: 10, “gameId”: 1 }

Пояснения: - title — название товара; - description — описание; - price
— цена; - sellerId — ID пользователя-продавца; - gameId — ID игры, к
которой относится товар.

Проверенные маршруты товаров:

Получить все товары: GET http://localhost:8080/api/items

Получить только доступные товары: GET
http://localhost:8080/api/items/available

Получить товар по ID: GET http://localhost:8080/api/items/3

Получить товары конкретного продавца: GET
http://localhost:8080/api/items/seller/10

Обновить товар: PUT http://localhost:8080/api/items/3

Удалить товар (мягкое удаление): DELETE
http://localhost:8080/api/items/3?sellerId=10

Мягкое удаление означает, что запись не обязательно удаляется из базы:
товар помечается как недоступный (available = false).

Для обновления товара используйте JSON с изменяемыми полями,
соответствующими Item. Если формат PUT отличается в текущем контроллере,
ориентируйтесь на ItemController.

8. ЗАКАЗЫ

Создание заказа: Метод: POST URL: http://localhost:8080/api/orders

Body -> raw -> JSON: { “buyerId”: 9, “itemId”: 3 }

Покупатель должен быть авторизован. В примере buyerId = 9, itemId = 3.

Логика создания заказа: - проверяется существование товара; -
проверяется доступность товара; - покупатель не может купить собственный
товар; - создаётся заказ со статусом NEW; - товар становится недоступным
для других покупок.

Получить список заказов: GET http://localhost:8080/api/orders

Основные операции с заказом реализованы в OrderService:

1.  Оплата заказа: payOrder(orderId, buyerId) Проверяется, что заказ
    принадлежит покупателю, статус NEW и баланса достаточно. Деньги
    списываются с покупателя, статус становится PAID.

2.  Подтверждение/доставка продавцом: deliverOrder(orderId, sellerId)
    Проверяется продавец и статус PAID. Деньги переводятся продавцу,
    статус становится DELIVERED.

3.  Отмена заказа покупателем или продавцом: cancelOrder(orderId,
    userId) Разрешена только для заказа NEW. Товар снова становится
    доступным, статус — CANCELLED.

4.  Открытие спора: openDispute(orderId, buyerId) Покупатель может
    открыть спор по заказу со статусом PAID. Статус становится DISPUTE.

5.  Отмена заказа администратором: cancelOrderByAdmin(orderId, adminId)
    Администратор может отменить заказ, если он ещё не DELIVERED и не
    CANCELLED. Если заказ был PAID или DISPUTE, деньги возвращаются
    покупателю. Товар снова становится доступным, заказ получает статус
    CANCELLED.

Точные HTTP-маршруты и JSON для оплаты, доставки, обычной отмены и спора
следует сверять с OrderController: в ходе предыдущей работы подтверждена
логика сервисных методов, но не все адреса контроллера зафиксированы.

9. АДМИНИСТРАТИВНЫЕ ОПЕРАЦИИ

Административные маршруты находятся под: /api/admin

Для запросов нужен JWT пользователя с ролью ADMIN.

Пример административной отмены заказа: Метод: POST URL:
http://localhost:8080/api/admin/orders/1/cancel

Authorization -> Bearer Token: токен администратора.

Body не требуется.

Пополнение баланса и другие административные операции доступны через
AdminController. Обычный пользователь не должен иметь возможность
выполнять административные операции.

В проекте для /api/admin/** настроено ограничение роли ADMIN.

10. ЧАТ ПОКУПАТЕЛЯ И ПРОДАВЦА

Чат работает через REST-запросы. Это не WebSocket: для получения новых
сообщений клиент повторно запрашивает историю или список диалогов.

Отправка первого сообщения покупателем: Метод: POST URL:
http://localhost:8080/api/chat/items/3/messages

Authorization: Bearer Token покупателя. Body: { “buyerId”: null,
“content”: “Здравствуйте! Товар ещё доступен?” }

Для покупателя buyerId можно передать null: покупатель определяется по
JWT-токену.

Ответ продавца: Метод: POST URL:
http://localhost:8080/api/chat/items/3/messages

Authorization: Bearer Token продавца. Body: { “buyerId”: 9, “content”:
“Здравствуйте! Да, товар доступен.” }

Продавец указывает ID покупателя, с которым уже существует переписка.

Получить историю переписки: Метод: GET URL:
http://localhost:8080/api/chat/items/3/messages?buyerId=9

Authorization: Bearer Token одного из участников переписки. Body не
требуется.

Получить список диалогов текущего пользователя: Метод: GET URL:
http://localhost:8080/api/chat/conversations

Authorization: Bearer Token пользователя. Body не требуется.

В списке диалогов возвращаются: - ID товара и название; - ID и имя
покупателя; - ID и имя продавца; - последнее сообщение, включая
отправителя, текст и дату.

Доступ к истории переписки разрешён только покупателю или продавцу,
участвующим в этом диалоге.

12. СТАТУСЫ ЗАКАЗА

NEW — заказ создан, но ещё не оплачен. PAID — заказ оплачен покупателем.
DELIVERED — продавец подтвердил выполнение/доставку. DISPUTE —
покупатель открыл спор. CANCELLED — заказ отменён.

Типичный сценарий: 1. Покупатель создаёт заказ — NEW. 2. Покупатель
оплачивает — PAID. 3. Продавец подтверждает выполнение — DELIVERED.

Альтернативный сценарий: 1. Заказ NEW можно отменить покупателю или
продавцу. 2. По оплаченному заказу покупатель может открыть спор —
DISPUTE. 3. Администратор может отменить заказ и вернуть деньги
покупателю.

13. ЧАСТЫЕ ПРОБЛЕМЫ

401 Unauthorized: - отсутствует токен; - токен неправильный или
устарел; - не выбран Bearer Token; - выполнен вход не под тем
пользователем.

403 Forbidden: - пользователь авторизован, но у него недостаточно
прав; - например, USER пытается вызвать административный маршрут.

404 Not Found: - указан неправильный ID товара, пользователя или
заказа; - объект не существует.

405 Method Not Allowed: - выбран неправильный HTTP-метод; - например,
отправлен GET вместо POST.

400 Bad Request: - JSON некорректен; - отсутствует обязательное поле; -
значение имеет неподходящий формат.

Ошибка подключения: - проверьте, запущен ли Spring Boot; - проверьте
адрес http://localhost:8080; - посмотрите текст ошибки в терминале VS
Code.

14. СТРУКТУРА ПРОЕКТА И НАЗНАЧЕНИЕ СЛОЁВ

entity — классы сущностей, которые соответствуют таблицам базы данных.
repository — интерфейсы доступа к данным через Spring Data JPA. service
— бизнес-логика: проверки, создание заказов, оплата, чат и другие
операции. controller — REST API: принимает HTTP-запросы и возвращает
ответы. dto — объекты для передачи данных между клиентом и сервером.
security — настройки Spring Security, JWT-фильтр и проверка токенов.

Принцип работы запроса: Postman -> Controller -> Service -> Repository
-> H2 Database. Ответ возвращается обратно клиенту в формате JSON.
